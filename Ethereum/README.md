# BankNode Ethereum Threshold ECDSA V1

Three cooperating Node.js processes control one Ethereum EOA and produce a
standard recoverable secp256k1 ECDSA signature only when any two of the three
nodes participate. The complete private key is never created during either DKG
or signing.

The interface and layout follow the Bitcoin project:

- `three-headed-bot.js` — entry point, peer HTTP(S), and DKG/sign orchestration;
- `crypto_backend.js` — cryptographic backend;
- `tg_backend.js` — Telegram polling, commands, and approval flow;
- `node-{1,2,3}.config.example.json` — configurations in the BTC version format;
- `data/` — each node's local secret share.

`crypto_backend.js`, `tg_backend.js`, and `three-headed-bot.js` contain the
complete implementation.

## Cryptographic model

- DKG: three participants independently create a secp256k1 contribution, a
  Shamir 2-of-3 share, a Feldman VSS commitment, and a 3072-bit Paillier key pair.
- Threshold signing: the corrected BitGo GG18 scheme with MtA, Paillier modulus
  challenge, range proofs, proof of share possession, and verifiable `V/A` and
  `U/T` commitment/decommitment stages.
- Result: a standard Ethereum low-S signature in `r || s || yParity` format. It
  can be verified with `ethers.recoverAddress`, geth, or any EVM tool.
- Transaction digests are signed as final 32-byte values without another
  SHA-256 operation. `/sign` and `/multisign` first apply EIP-191 `hashMessage`.
- `/send` and `/multisend` build EIP-1559 transactions, estimate gas,
  threshold-sign `unsignedHash`, verify the recovered address locally, and only
  then submit the raw transaction to an RPC node.
- `/tokensend` and `/multitokensend` similarly build an ERC-20
  `transfer(address,uint256)` call with `value = 0`, verify contract code,
  `decimals`, token balance, the simulation result, and the ETH available for gas.

As in the BTC version, each node's public contribution is derived
deterministically from `crypto.masterSeed_fix`, the Telegram wallet key, and
fixed parameters using HMAC-SHA512. Deleting the database and repeating DKG
with the same `_fix` fields therefore reproduces the same Ethereum address.
Paillier keys, Shamir polynomials, and signing nonces are still generated by the
system CSPRNG and differ on every run. Losing one share file is tolerated;
losing any two requires a new DKG.

## Installation

Node.js 20+ is required.

```bash
npm ci
npm run check
npm test
```

The full test generates real 3072-bit Paillier keys for all three parties and
performs a complete 2-of-3 Ethereum signature. Only the auxiliary RSA modulus
is reduced to 512 bits in the test for speed; runtime always calls
`generateNtilde(3072)`.

All parameters and secrets are stored directly in `node-*.config.json`;
environment variables are not used. Copy the appropriate
`.config.example.json` to `.config.json` and replace all `PASTE_*` and
`REPLACE_*` values.

In each config, set `telegram.botToken`, `telegram.allowedGroupId`, and a unique
`crypto.masterSeed_fix` containing at least 32 bytes. The
`ethereum.providers[].baseUrl` entries already contain three public Ethereum
Mainnet RPC endpoints, used in order with automatic failover.
`http.tls.certPem` and `http.tls.keyPem` accept either PEM text embedded directly
in JSON or a path relative to the config file. Set `runtime.environment` to
`production` to make TLS mandatory. In `development`, inter-node HTTPS accepts
self-signed certificates, matching the BTC version. In `production`, the
certificate is always validated against the system CA store.

The example configs use loopback HTTP for local testing. For production:

1. Deploy the nodes on separate machines and in separate security domains.
2. Fill in `http.tls.certPem` and `http.tls.keyPem`.
3. Use `https://...` peer URLs and certificates signed by a system-trusted CA.
4. Do not set `rejectUnauthorized: false`; production validation prohibits it.
5. Keep `data/*.db` on encrypted storage with separate backups and ACLs.
6. Set `runtime.environment` to `production` and use the pinned `package-lock.json`.

Start the nodes:

```bash
npm start -- node-1.config.example.json
npm start -- node-2.config.example.json
npm start -- node-3.config.example.json
```

The default Ethereum peer ports are `6661`, `6662`, and `6663`.

During `/create`, after DKG transcript verification, all three nodes generate
their reusable 3072-bit `Ntilde` signing parameters in parallel and persist them
in their local databases. This makes `/create` slower, but removes safe-prime
generation from the first signing operation. Repeating `/create` for an existing
wallet does not rerun DKG; it only ensures that the signing parameters exist on
all three nodes.

The Telegram `/create` response reports the total elapsed time and the `Ntilde`
precomputation time for every node in milliseconds. `generated` means that the
node created and persisted new parameters; `cached` means it validated and
reused the stored parameters. Node times must not be added because the work runs
in parallel.

All inter-node `/create` stages use a 60-minute setup timeout so that 3072-bit
Paillier and `Ntilde` generation can complete on slower processors. Ordinary
signing requests retain their shorter timeouts.

Telegram `sendMessage` calls use a 10-minute client timeout so CPU-heavy MPC
rounds cannot turn an already delivered acknowledgement into a false command
error. A reply-delivery failure is logged separately and does not change the
result of an already completed signing or broadcast operation.

For detailed console timing of Ethereum RPC, approvals, peer requests, challenge
handling, and MPC signing rounds, set `runtime.logLevel` to `debug` in every node
config and restart all three processes. The supported levels are `debug`,
`info`, `warn`, `error`, and `fatal`; the default example value is `info`.

## Telegram commands

Commands are accepted only from `allowedGroupId` and must be addressed to the bot.

```text
/create@bot
/create@bot <user_id2> <user_id3>
/address@bot
/balance@bot [address]
/tokenbalance@bot <token_contract> [owner]
/usdtbalance@bot [owner]
/utxo@bot
/status@bot
/sign@bot <message>
/signhash@bot <32-byte-hex>
/send@bot <to> <amount_wei> [max_fee_gwei]
/tokensend@bot <token_contract> <to> <amount_tokens> [max_fee_gwei]
/usdtsend@bot <to> <amount_usdt> [max_fee_gwei]
/multisign@bot <id2> <id3> <message>
/multisignhash@bot <id2> <id3> <32-byte-hex>
/multisend@bot <id2> <id3> <to> <amount_wei> [max_fee_gwei]
/multitokensend@bot <id2> <id3> <token_contract> <to> <amount_tokens> [max_fee_gwei]
/usdtmultisend@bot <id2> <id3> <to> <amount_usdt> [max_fee_gwei]
/approve@bot
/reject@bot
```

As in the BTC version, `user_id2` and `user_id3` may be equal to each other or
to the initiator's ID; duplicates are retained in the canonical group key.

For `/send` and `/multisend`, `amount_wei = 0` enables send-all mode. The system
uses the pending balance and signs the actual value
`balance - gasLimit * maxFeePerGas`, reserving the maximum possible EIP-1559
fee. If the actual `effectiveGasPrice` is below `maxFeePerGas`, the unused fee
reserve remains at the source address after mining, so the final balance may be
non-zero.

`amount_tokens` is specified in display units, for example `1.25` for a token
with six decimal places. The backend obtains `decimals()` from the contract and
converts the amount to integer base units without floating-point arithmetic.
`/tokenbalance` and `/usdtbalance` without `owner` list the user's personal
threshold address and every group wallet that contains the user. The personal
address is shown first. With an explicit `owner`, only that address is queried.

`/usdtbalance`, `/usdtsend`, and `/usdtmultisend` are safe aliases for Ethereum
Mainnet USDT at the fixed official address
`0xdAC17F958D2ee523a2206206994597C13D831ec7`. They operate only when
`ethereum.chainId = 1`; the user cannot supply or substitute the token address.

`/utxo` is retained for interface compatibility and returns the Ethereum nonce
and balance because account-based Ethereum has no UTXO set.

`/balance` without an address lists the personal wallet first and then every
group wallet whose member list contains the requesting Telegram user, including
the address and ETH balance of each wallet. `/balance <address>` queries only
the explicitly supplied Ethereum address.

Before each signature, the second signer publishes the digest and operation
description. In personal mode, the initiator approves or rejects it through the
second node's bot. In group mode, one of the two additional Telegram IDs must
approve; rejection is replaced by a timeout, matching the original interface.

An explicit personal-mode `/reject` is final for that transaction: the
coordinator stops immediately and does not ask another signer. Automatic
fallback to the next configured signer is allowed only when the first signer is
unreachable, its peer request times out, or the approval itself times out.
Protocol and validation errors also stop the operation instead of causing a new
approval request.

## Network protocol and storage

The peer configuration format matches the BTC version: `index_fix`, `id`, `ip`,
and `port`. A peer is identified by protocol/node ID headers; there is no
separate application-level HMAC authentication. In production, inter-node ports
must be restricted by network ACL to participant addresses only, and HTTPS must
use certificates signed by a system-trusted CA.

Secret DKG shares are transmitted directly to the recipient, not through the
coordinator. Database writes use a temporary file followed by an atomic rename;
the POSIX mode is `0600`. In-flight signing nonce/state is never persisted: after
a crash, the ceremony must start again.

## Production limitations

This is a complete cryptographic implementation, but it is not a claim that the
entire system has completed a security audit. Before storing real value, obtain
an independent audit of the exact commit, protocol transcript fuzzing, mTLS/HSM
or enclave protection for shares, rollback-resistant storage, rate limits,
monitoring, and backup/disaster-recovery runbooks. Telegram should be treated as
an approval UI, not as the only authentication factor for high-value custody.
